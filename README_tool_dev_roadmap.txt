================================================================================
                    NANO_HARNESS — КАК ПИСАТЬ НОВЫЕ ИНСТРУМЕНТЫ
================================================================================

Файл для разработчика. О том, как добавить новый инструмент, как проверить,
что он работает, и как откалибровать константы отбора через тест.

--------------------------------------------------------------------------------
ЧТО ТАКОЕ ИНСТРУМЕНТ
--------------------------------------------------------------------------------

Инструмент — это функция, которую LLM может вызвать через tool_calls.
Модель видит описание и JSON-схему параметров в API-запросе (поле tools).
Harness исполняет функцию и возвращает JSON-строку с результатом.

Три части:

1. Определение (name, description, parameters) — то, что видит модель.
2. Обработчик (async fn run) — код, который исполняется при вызове.
3. Регистрация — автоматическая через inventory.

Всё живёт в src/tool_runtime/tools/.

--------------------------------------------------------------------------------
КАКИЕ БЫВАЮТ ИНСТРУМЕНТЫ
--------------------------------------------------------------------------------

По природе:

- Читающие. Ничего не меняют. storage_read_file, storage_walk, storage_list_dir.
- Пишущие. Меняют состояние. storage_write_file, storage_delete_file.
- Сетевые. Обращаются к другим сервисам. call_agent, post_task.
- Вычислительные. Обрабатывают данные без побочных эффектов.

--------------------------------------------------------------------------------
ШАГ 1. СОЗДАТЬ ФАЙЛ
--------------------------------------------------------------------------------

Один инструмент — один файл в src/tool_runtime/tools/.
Имя файла = имя инструмента в snake_case.

    src/tool_runtime/tools/storage_read_file.rs

--------------------------------------------------------------------------------
ШАГ 2. РЕАЛИЗОВАТЬ ТРЕЙТ
--------------------------------------------------------------------------------

Каждый инструмент — это структура (unit struct, без полей) и impl трейта
ToolImpl. Трейт определён в src/tool_runtime/mod.rs.

    use crate::tool_runtime::context::ToolContext;
    use crate::tool_runtime::primitives::{err, ok_text, parse_input, require_string};
    use crate::tool_runtime::ToolImpl;

    pub struct StorageReadFile;

    #[async_trait::async_trait]
    impl ToolImpl for StorageReadFile {
        fn name(&self) -> &'static str {
            "storage_read_file"
        }

        fn description(&self) -> &'static str {
            "Читает содержимое файла в локальном хранилище. \
             Возвращает текст файла. При ошибке — JSON с полем 'error'."
        }

        fn parameters(&self) -> serde_json::Value {
            serde_json::json!({
                "type": "object",
                "properties": {
                    "path": {
                        "type": "string",
                        "description": "Путь к файлу относительно корня проекта"
                    }
                },
                "required": ["path"]
            })
        }

        async fn run(&self, input: &str, ctx: &ToolContext) -> String {
            // ... сама логика ...
        }
    }

    inventory::submit! {
        &StorageReadFile as &'static dyn crate::tool_runtime::ToolImpl
    }

Четыре метода:

- name         — имя инструмента. Оно же указывается в config.toml.
- description  — что делает. Модель читает и решает, звать ли.
- parameters   — JSON Schema параметров.
- run          — сама логика. Принимает JSON-строку, возвращает JSON-строку.

--------------------------------------------------------------------------------
ОПИСАНИЕ — ЭТО КОНТРАКТ ДЛЯ ДВУХ МЕХАНИЗМОВ
--------------------------------------------------------------------------------

description тулза используется не только моделью, но и механизмом
select_tools. Это вторая и неочевидная роль описания.

Как работает select_tools:

1. YAKE по промпту пользователя → N ключевых фраз.
2. Каждая фраза — семантический поиск по индексу .tools/.
3. Индекс .tools/ — это файлы <имя>.md, в каждом name + description.
4. Кандидаты ранжируются по distance и score, top-N попадают в видимые
   модели тулзы на текущий ход.
5. Плюс всегда добавляются call_agent и post_task (см. ниже).

Description содержит две части:

1. Пользовательские якоря — слова, которыми задача формулируется
   в промпте: «прочитай», «посчитай», «найди», «создай». Именно они
   определяют distance в семантическом поиске. Размещаются в начале
   описания.

2. Контракт для модели — что тулз делает и что возвращает, включая
   технические детали («Возвращает JSON-массив объектов вида...»,
   «Возвращает 'OK' при успехе»). Эти детали нужны LLM при вызове,
   но на distance влияют слабо.

Если в описании отсутствуют якоря, distance остаётся высоким
независимо от объёма технической части, что плохо.

Пример из практики. Тулз storage_search_similar имел описание
«Семантический поиск файлов по смыслу запроса. Возвращает JSON-массив...».
На запросе «найди что-нибудь похожее на X» distance был около 0.81.
После добавления «Находит файлы, похожие (близкие по смыслу) на запрос»
distance упал в рабочий диапазон. Мы добавили фразу, а не удалили хвост.

Правила формулировки description:

- Первое предложение — что делает тулз, словами пользователя.
- Добавляй синонимы в скобках: «директорию (папку, каталог)».
- Не удаляй существующее — только добавляй. Информация о возвращаемом
  («Возвращает 'OK' при успехе») полезна модели и должна остаться.
- Никакого keyword stuffing. Только то, что пользователь мог бы написать.

--------------------------------------------------------------------------------
ЧТО ВСЕГДА ВИДНО МОДЕЛИ
--------------------------------------------------------------------------------

Независимо от select_tools, в visible_tools всегда добавляются два тулза:

- call_agent
- post_task

Они прописаны константой в src/tool_search.rs. Если тулз есть в allowed
(то есть в tools агента или [[tools]] чата), он попадёт в видимый набор
на любом ходу, даже если промпт про него ни слова.

Это исключение из общей схемы. Добавлять в этот список другие тулзы
без явной причины не нужно — они должны попадать через обычный отбор.

--------------------------------------------------------------------------------
ШАГ 3. ДОБАВИТЬ В mod.rs
--------------------------------------------------------------------------------

Файл: src/tool_runtime/tools/mod.rs.

    mod storage_read_file;
    pub use storage_read_file::StorageReadFile;

Это единственное место, где надо прописывать что-то руками. Одна строка
mod, одна строка pub use на каждый инструмент. Всё остальное (списки для
модели, диспетчер вызовов) собирается автоматически из inventory.

--------------------------------------------------------------------------------
ШАГ 4. РАЗРЕШИТЬ В КОНФИГЕ
--------------------------------------------------------------------------------

Инструменты разрешаются в config.toml. У чата — в [[tools]], у каждого
агента — в его секции tools = [...].

    [[agents]]
    name = "assistant"
    tools = ["storage_read_file", "storage_write_file", "storage_walk"]

Или для чата:

    [[tools]]
    name = "storage_read_file"
    mode = "auto"

--------------------------------------------------------------------------------
ШАГ 5. СОБРАТЬ И ЗАПУСТИТЬ
--------------------------------------------------------------------------------

1. cargo build --release
2. Запустить хранилище, доску, агента (или control_center → Start all).

Индекс .tools/ пересобирается при старте local_storage_http_server из
inventory. Тулз, зарегистрированный в коде, автоматически попадёт в
индекс при следующем запуске хранилища. Отдельно что-то писать в .tools/
руками не нужно.

--------------------------------------------------------------------------------
ШАГ 6. ПРОВЕРИТЬ
--------------------------------------------------------------------------------

Базовые проверки:

1. Дать агенту задачу, которая должна использовать новый инструмент.
2. Смотреть лог агента:
   - строка tool_request с именем тулза и аргументами — модель его вызвала;
   - строка tool_result с результатом — тулз отработал.
3. Если тулз не вызывается — модель его не видит. Проверь:
   - имя есть в config.toml;
   - агент перезапущен;
   - описание не пустое;
   - тулз попал в visible_tools (см. ниже).
4. Если вызывается, но падает — смотри текст ошибки в tool_result.

Проверка через visible_tools:

В логе чата и агента печатается строка вида:

    🔧 visible_tools: ["scc", "ripgrep", "call_agent", "post_task"]

Что тут смотреть:

- Есть ли новый тулз в списке на типичном для него запросе.
- Нет ли его на запросе, где он точно не нужен (иначе description
  слишком широкий и цепляется за чужие слова).
- Если тулз на запросе про него отсутствует — значит, distance выше
  threshold или score ниже min_score. Калибровка через тест (см. ниже).

Проверка через тест:

Основной способ убедиться, что описание работает и константы подобраны —
запустить probe-тест. См. раздел ТЕСТЫ.

--------------------------------------------------------------------------------
ТЕСТЫ
--------------------------------------------------------------------------------

Probe-тест — это способ проверить, как тулз ложится в векторный индекс
и как ведут себя константы отбора на реальных промптах. Файл:

    tests/tool_search_probe.rs

Что делает тест:

1. Пересобирает .tools/ из inventory.
2. Прогоняет список запросов (заданных в коде теста).
3. Для каждого запроса печатает топ-N тулзов по score, с полями:
   - имя,
   - score,
   - hits (сколько YAKE-фраз запроса нашли тулз),
   - min_dist (минимальный distance).

Запуск:

    cargo test --release --test tool_search_probe -- --nocapture

Флаг --release обязателен. В debug-сборке векторный поиск медленный
на порядок.

Как добавить свой запрос:

В файле tests/tool_search_probe.rs найти массив queries и добавить туда
строку с типичным пользовательским промптом для нового тулза.

    let queries: &[&str] = &[
        "посчитай строки кода",
        "найди упоминания tokio в проекте",
        "прочитай файл README.md",
        // новый запрос:
        "мой новый запрос под новый тулз",
    ];

Как читать результат:

Для каждого запроса тест печатает:

    QUERY: "посчитай строки кода"
      1. scc             score=0.5053  (hits=3, min_dist=0.4105)
      2. code_index      score=0.3632  (hits=3, min_dist=0.5762)
      3. ctags           score=0.3485  (hits=3, min_dist=0.5934)

Что смотреть:

- Новый тулз должен быть в топе (в первых N строках).
- min_dist правильного тулза должен быть ниже threshold.
- score правильного тулза должен быть выше min_score.

Как проверять константы:

Константы отбора лежат в config.toml, секция плоская, ключи
tools_search_*. Каждая влияет на своё:

- tools_search_top_n — сколько YAKE-фраз берётся из промпта.
  Больше → больше кандидатов, но и больше шума. Обычно 5–7.
- tools_search_phrase_min_words — минимум слов в фразе. 2 — разумный
  дефолт. 1 пропускает односложный шум, 3 режет короткие запросы.
- tools_search_threshold — максимальный distance для попадания в hits.
  Определяется по расстоянию правильных и мусорных срабатываний в
  probe-тесте. Если правильный тулз даёт dist 0.6, а мусорный — 0.83,
  threshold ставится между: 0.7 или 0.75.
- tools_search_slots — размер динамической части visible_tools.
  Сколько тулзов в топе. 3–4 разумно.
- tools_search_min_score — минимальный score кандидата. Отсекает
  случайные попадания на мусорных промптах. Если на «расскажи анекдот»
  лучший score = 0.11, а на правильных запросах минимум = 0.28,
  min_score ставится между: 0.15 или 0.2.

Методика калибровки:

1. Прогнать probe с широким набором запросов — правильных и мусорных.
2. Посмотреть распределение min_dist по правильным тулзам и по мусору.
3. Найти зазор. threshold — в этом зазоре.
4. Аналогично со score: посмотреть score мусора и правильных, найти
   зазор, поставить min_score внутри.
5. Если зазора нет (правильное и мусор переплетаются) — проблема не
   в константах, а в описании конкретного тулза. Править description.

Правка констант — в config.toml, без пересборки. Но перезапустить
сервисы всё равно надо.

--------------------------------------------------------------------------------
ТЕСТИРОВАНИЕ ПРАВОК ОПИСАНИЯ
--------------------------------------------------------------------------------

Любая правка description существующего тулза — это правка семантического
индекса. Она меняет поведение select_tools, а не только текст для модели.

Правильный порядок:

1. Изменить description в файле тулза.
2. cargo build --release.
3. Перезапустить local_storage_http_server (чтобы .tools/ пересобрался).
4. Прогнать probe-тест.
5. Сравнить distance и score до и после.

Если после правки тулз стал чаще появляться там, где не нужен, или,
наоборот, пропал там, где нужен — откатить. Описание — не текст «для
красоты», а часть контракта.

--------------------------------------------------------------------------------
ДОСТУПНЫЙ КОНТЕКСТ
--------------------------------------------------------------------------------

Обработчик получает &ToolContext. В нём:

    http_client            reqwest::Client        клиент для HTTP-запросов
    storage_base_url       String                 адрес хранилища (с http://)
    storage_auth_token     String                 токен хранилища
    board_base_url         String                 адрес доски (с http://)
    board_auth_token       String                 токен доски
    project_id             String                 проект, в котором идёт работа
    session_id             Option<String>         сессия вызывающего
    parent_chain           Vec<String>            цепочка вызовов агентов
    self_agent_name        String                 имя вызывающего ("chat" для чата)
    pending_calls          PendingCalls           ожидающие синхронных вызовов
    outgoing_tasks         OutgoingTasks          исходящие асинхронные задачи
    agent_call_timeout_sec u64                    таймаут call_agent

project_id нужен для запросов к хранилищу — идёт в заголовок X-NH-Project.
parent_chain нужен для call_agent / post_task — защита от циклов.

Хелперы (в ctx):

    ctx.storage_base()  -> &str  адрес хранилища без завершающего слэша
    ctx.board_base()    -> &str  адрес доски без завершающего слэша

--------------------------------------------------------------------------------
ПРИМИТИВЫ (src/tool_runtime/primitives.rs)
--------------------------------------------------------------------------------

Готовые функции для типовых операций внутри run.

    parse_input(input)                  -> Result<Value, String>
        Парсит входную JSON-строку. Пустая строка → пустой объект.

    require_string(&args, "path")       -> Result<String, String>
        Извлекает обязательный строковый параметр. Возвращает Err с понятным
        текстом, если параметр отсутствует или пуст.

    optional_string(&args, "name")      -> Option<String>
        Опциональный строковый параметр.

    optional_int(&args, "top_k")        -> Option<i64>
        Опциональный целочисленный параметр.

    ok_text("результат")                -> String
        Успешный ответ. Оборачивает произвольный текст в JSON:
        {"ok": true, "content": "результат"}

    ok_json(value)                      -> String
        Успешный ответ с произвольным JSON-объектом:
        {"ok": true, "data": {...}}

    err("сообщение")                    -> String
        Ошибка:
        {"ok": false, "error": "сообщение"}

Всегда возвращай через ok_text или err. Модель видит поле ok и понимает,
успех это или провал.

--------------------------------------------------------------------------------
ПРИМЕР. ИНСТРУМЕНТ, ВЫЗЫВАЮЩИЙ ДРУГОЙ СЕРВИС (call_agent)
--------------------------------------------------------------------------------

Сложнее. Публикует задачу на доске, ждёт ответа через pending_calls.

    async fn run(&self, input: &str, ctx: &ToolContext) -> String {
        let args = match parse_input(input) { Ok(v) => v, Err(e) => return err(e) };
        let to_agent = match require_string(&args, "to_agent") { Ok(a) => a, Err(e) => return err(e) };
        let prompt = match require_string(&args, "prompt") { Ok(p) => p, Err(e) => return err(e) };

        // Проверки на самовызов и цикл.
        if to_agent == ctx.self_agent_name { ... }
        if ctx.parent_chain.contains(&to_agent) { ... }

        // 1. POST /tasks на доске.
        // 2. Получаем task_id.
        // 3. Кладём oneshot-канал в ctx.pending_calls под этим task_id.
        // 4. tokio::time::timeout(rx).await с ctx.agent_call_timeout_sec.
        // 5. На таймауте — POST /tasks/{id}/fail, вернуть err.

        // ... полностью расписано в src/tool_runtime/tools/call_agent.rs ...
        ok_text("ответ")
    }

Ключевое: обработчик асинхронный, работает в tokio-контексте, никаких
block_on, никакого Handle::current. reqwest::Client из ctx.http_client.

--------------------------------------------------------------------------------
ЧЕГО НЕ ДЕЛАТЬ
--------------------------------------------------------------------------------

1. Не создавать reqwest::blocking::Client внутри async-обработчика. Это
   дропает runtime в неправильном месте и роняет процесс. Только async
   reqwest::Client из ctx.http_client.

2. Не использовать std::sync::Mutex в горячем пути. Только tokio::sync::Mutex
   и .lock().await.

3. Не паниковать при ошибках. unwrap и expect — только там, где сбой
   действительно невозможен. Всё остальное — return err(...).

4. Не смешивать sync и async. Если обработчик async, всё внутри async.
   Если нужна блокирующая операция — spawn_blocking с явным замыканием.

5. Не добавлять инструмент с неясным описанием. Модель его не вызовет,
   select_tools его не найдёт. Описание — часть контракта.

6. Не прописывать инструмент вручную в списках для модели. available_tools
   собирается автоматически из inventory. Единственное место с ручной
   регистрацией — mod.rs в tool_runtime/tools.

7. Не менять description существующих тулзов без прогона probe-теста.
   Description — часть семантического индекса. Правка меняет поведение
   select_tools на всех промптах, а не только на целевом.

8. Не добавлять тулзы в ALWAYS_VISIBLE (call_agent, post_task) без
   крайней необходимости. Это глобальное исключение, для него нужна
   причина, а не «так удобнее».

ШПАРГАЛКА
--------------------------------------------------------------------------------

Новый инструмент за 5 шагов:

    1. src/tool_runtime/tools/<имя>.rs   — структура + impl ToolImpl + inventory::submit!
    2. src/tool_runtime/tools/mod.rs     — mod <имя>; pub use ...;
    3. config.toml                       — вписать имя в tools нужных агентов
    4. cargo build --release
    5. перезапустить сервисы (хранилище пересоберёт .tools/ из inventory)

Проверить:

    - в логе агента/чата: 🔧 visible_tools: [...]
    - в логе агента: tool_request и tool_result
    - probe: cargo test --release --test tool_search_probe -- --nocapture

Признаки проблем:

    - Модель не зовёт инструмент — его нет в config.toml, плохое описание,
      или distance выше threshold.
    - Инструмент падает — смотри текст ошибки в tool_result, чаще всего
      неверные аргументы или недоступный сервис.
    - Паника процесса — где-то блокирующий вызов в async-контексте.
    - Инструмент лезет в visible_tools на неподходящих запросах — слишком
      широкое описание, нужно сужать.
    - Инструмент пропадает из visible_tools на своих запросах — description
      без пользовательских якорей, добавить синонимы.

--------------------------------------------------------------------------------
ФИЛОСОФИЯ
--------------------------------------------------------------------------------

Инструмент — это контракт между тобой и моделью. Ты описываешь, что функция
делает и какие у неё параметры. Модель решает, когда её вызывать. Harness
следит за тем, чтобы вызов был корректным и результат вернулся.

Описание тулза работает в двух местах одновременно: как контракт для модели
(«что делает») и как запись в семантическом индексе для select_tools
(«на что похоже в терминах пользователя»). Обе роли надо держать в голове.

Чем проще инструмент, тем надёжнее. Один инструмент — одно действие.
Составные инструменты (read_many, walk_with_content) — когда нужно закрыть
частый сценарий без N round-trip. Но не увлекаться: каждый новый инструмент
это ещё одна вещь, о которой модель должна помнить, и ещё одна запись в
индексе .tools/, отбираемая на каждом ходу.

Инструментов должно быть столько, сколько нужно, и ни одним больше.
