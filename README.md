# nano_harness

nano_harness — это harness для одного разработчика. Агенты работают как отдельные сервисы, общаются через доску задач, делят файловое хранилище с семантическим поиском. Всё, что можно удержать на машине, остаётся на машине: файлы, история, память, скиллы, выговоры. Наружу уходят только запросы к LLM.

И ничего не спрятано. Каждый вызов инструмента, каждый запрос к модели, каждое решение агента видно в логах и в консоли. Управление — через конфиг и команды, а не через чёрный ящик.

- **`control_center`** — графическая консоль для запуска и остановки сервисов.
- **`agent_server`** — сервер одного агента.
- **`local_storage_http_server`** — файловое хранилище с векторным поиском.
- **`message_board_server`** — шина задач и событий между агентами.

## 🤔 Что такое Agent Harness

LLM умеет генерировать текст. Чтобы она могла читать файлы, вызывать инструменты, звать других агентов, помнить прошлые решения и не уходить в бесконечный цикл вызовов, ей нужна обвязка. Модель даёт интеллект. Harness даёт руки, глаза, память и границы.

nano_harness — это реализация такого harness на Rust. Не для одной модели, а для нескольких агентов сразу, с общей шиной задач, общим хранилищем и общим механизмом накопления опыта. Проект рассчитан на локальный запуск и одного пользователя: не потому что не может быть иначе, а потому что так задуман. Никакой мультитенантности, никаких ролей, никакой сложной аутентификации. Один разработчик, его машина, его агенты.

## 🚀 Быстрый старт

### 1. Сборка

```bash
git clone <repo>
cd nano_harness
cargo build --release
```

### 2. Модель эмбеддингов

Семантический поиск работает на модели `paraphrase-multilingual-MiniLM-L12-v2`. Её нужно скачать с Hugging Face и положить в `.models/paraphrase-multilingual-MiniLM-L12-v2/`. Нужны три файла: `config.json`, `tokenizer.json`, `model.safetensors`.

### 3. Конфигурация

API-ключ для языковой модели указывается в `config.toml` или в `.env` как `POLZA_API_KEY`. Для godfather можно задать отдельный `GODFATHER_API_KEY`, если хочется использовать под сжатие контекста другую модель.

### 4. Запуск

Через `control_center` — она поднимает сервисы в правильном порядке и следит за их состоянием. Либо вручную, четырьмя командами в отдельных терминалах:

```bash
cargo run --release --bin local_storage_http_server
cargo run --release --bin message_board_server
cargo run --release --bin agent_server -- --agent-name assistant
cargo run --release
```

Последняя команда открывает чат — интерактивную консоль, из которой можно работать с моделью напрямую или звать агентов.

### 🔄 Цикл агента

Работа агента — это цикл, в котором модель и инструменты обмениваются сообщениями, пока модель не выдаст финальный ответ. Модель решает, что делать. Harness решает, как это выполнить — безопасно, прозрачно, с полным логированием. Каждый шаг пишется в файл сессии, каждое обращение к инструменту — в отдельную строку лога.

Но между «получил задачу» и «вызвал модель» есть ещё два шага, которые harness делает сам, до первого обращения к API.

**Поиск скилла.** Если агент работает в auto-режиме и промпт не пустой, harness ищет подходящий скилл по семантической близости описания к задаче. Если расстояние ниже порога автовыполнения — код скилла запускается напрямую, минуя LLM. Модель вообще не вызывается, ответ возвращается сразу, расходы — ноль. Если расстояние в средней зоне, скилл кладётся в отдельный слот контекста как подсказка, и уже после этого начинается обычный цикл. Если ничего подходящего нет, работа идёт с чистого листа.

**Слот скилла — один, не стек.** Когда harness инжектит найденный скилл, он не добавляет новое system-сообщение к предыдущим, а перезаписывает предыдущий инжект. Перед каждым новым ходом слот очищается. Это защищает от накопления подсказок из прошлых задач, которые могут быть уже нерелевантны.

**Сам цикл.** После этих шагов начинается обычный обмен с моделью:

```python
while True:
    response = LLM.send(messages, tools)

    if response не содержит tool_calls:
        break

    for tool_call in response.tool_calls:
        result = execute_tool(tool_call)
        messages.append(result)
```

Инструменты исполняются в песочнице с ограничениями. Результат каждого вызова возвращается в модель, и она решает, что делать дальше: вызвать ещё один инструмент, задать уточняющий вопрос или выдать финальный ответ.

**Сохранение скилла.** Когда цикл завершился финальным ответом, а в ходе работы был хотя бы один успешный `run_code` — harness может сохранить этот код как новый скилл. Условия: код длиннее минимального порога, его AST не совпадает с уже существующими скиллами этого агента. Название и описание для нового скилла генерируются отдельным запросом к LLM. После успешного сохранения скилл попадёт в каталог и будет доступен при следующем поиске.

**Финализация хода.** Когда пользователь отправляет следующее сообщение, текущий ход перестаёт быть активным и уходит в историю. В этот момент harness делает две вещи. Первое: обнуляет reasoning у assistant-сообщений — для следующих ходов он не нужен, модель свои прошлые мысли не перечитывает. Второе: компактизирует тела крупных tool-результатов, заменяя их на плейсхолдер с указанием размера. Аргументы вызовов остаются видны, тела результатов — нет. Если модель снова захочет те же данные, она просто вызовет инструмент заново.

После финализации ход попадает либо в префикс, если пользователь закрепил его командой `/fix`, либо в хвост скользящего окна. Хвост обрезается по двум лимитам одновременно: по количеству ходов и по объёму в байтах.

## ✨ Features

### 🔧 Rhai-инструменты

Основной инструмент агента — `run_code`. Модель вызывает его через API, передавая в аргументах текст скрипта на Rhai. Движок исполняет скрипт в песочнице и возвращает строку с результатом, которая уходит обратно в модель.

Песочница ограничивает: миллион операций, шестьдесят четыре уровня вложенности вызовов, 256 килобайт на строку. Этого хватает для типичных задач и достаточно мало, чтобы ошибка в скрипте не заморозила агента.

Внутри Rhai доступны:

| Категория | Функции |
|-----------|---------|
| **Хранилище** | `storage_read_file`, `storage_write_file`, `storage_delete_file`, `storage_create_dir`, `storage_list_dir`, `storage_walk`, `storage_search_by_name`, `storage_search_similar`, `storage_read_about`, `storage_write_about`, `storage_read_summary`, `storage_write_summary` |
| **Агенты** | `call_agent` (синхронно), `post_task` (асинхронно) |
| **Данные** | `parse_json`, `slice`, `join` |
| **Базовое** | `get_time`, `get_weather` |

### 📚 Скиллы

Скиллы работают в двух режимах. В `auto` обёртка вокруг агента управляет всем сама: перед запросом к модели ищет подходящий скилл по семантической близости описания к промпту, после успешного `run_code` генерирует название и описание через LLM и сохраняет новый скилл. В `manual` обёртка не вмешивается, и агент управляет скиллами сам — через Rhai-функции `skill_search`, `skill_load`, `skill_save`, `skill_list`, `skill_record_usage`. Это даёт больше контроля, но требует, чтобы модель сама понимала, когда искать и когда сохранять.

Независимо от режима, поиск идёт по описанию. Если расстояние до ближайшего скилла ниже порога автовыполнения — код запускается напрямую, минуя LLM. Это экономит деньги и время. Если расстояние в средней зоне — скилл подмешивается в контекст как подсказка, но модель всё равно вызывается, уже с готовым решением перед глазами. Если ничего близкого нет — работа с чистого листа.

Скиллы сохраняются как файлы в `.local_storage/<storage_name>/.skills/`. У каждого скилла — название, описание, исходный промпт и код. Дедупликация идёт по хэшу AST: один и тот же код не сохраняется дважды, даже если модель написала его заново. Статистика успехов и неудач ведётся в каталоге `skills_catalog.json`.

Скиллы бывают только у агентов. Чат работает без них: там важнее прозрачность потока, чем экономия на эвристиках.

### 🧠 Контекст и память

Диалог с моделью не может расти бесконечно — каждый токен стоит денег, и у любой модели есть предел окна. Контекст делится на три части: system-промпт, префикс и хвост. System-промпт — это инструкции и роль. Префикс — то, что пользователь явно закрепил как важное командой `/fix`. Хвост — скользящее окно последних ходов, ограниченное двумя лимитами одновременно: по количеству ходов и по объёму в байтах. Ход вылетает, если его выкидывает хотя бы один из лимитов. Самый свежий ход не вылетает никогда, даже если он один больше бюджета.

Поверх этого работает компактизация. Когда ход завершается и уходит из активного диалога в хвост, тела крупных tool-результатов заменяются на короткий плейсхолдер с указанием размера. Аргументы вызова остаются видны — понятно, что модель делала. Тело результата не остаётся — платить за него в каждом следующем запросе больше не нужно. Если модели понадобятся те же данные, она просто вызовет инструмент заново.

Отдельная команда `/godfather` прогоняет хвост через вторую LLM, которая переписывает диалог короче. Сохраняются реплики пользователя, ответы ассистента, факты, решения и договорённости; выбрасываются повторы, промежуточные рассуждения, отвергнутые гипотезы и вода. Оригиналы уходят в архив и остаются доступны через `/unfreeze` — можно вернуть всё или только последний сжатый ход. Если сжатие не удалось или результат не короче оригинала — откат, ничего не меняется. Семантическое сжатие никогда не портит контекст молча.

### 🛡️ Rebuke

Пользователь может корректировать поведение агента через выговоры. Команда `/rebuke <agent> <текст>` дописывает замечание в файл агента, а при следующем старте агента содержимое файла вшивается в конец system-промпта. Всё дословно, без переформулировок через LLM: пользователь сам решает, что и как написать. Формат — блоки с датой и временем, разделённые пустой строкой. Изменения вступают в силу после перезапуска агента — это ожидаемое поведение, чат об этом явно сообщает. Отдельная команда `/rebuke_edit <agent>` открывает файл в редакторе для ручной правки: убрать устаревшее, переформулировать, удалить противоречия.

### 🤝 Мультиагентность

Доска задач — это шина, через которую агенты общаются. Один агент публикует задачу для другого, доска доставляет её через SSE, ждёт ответа и возвращает его отправителю. Состояние задач хранится на диске, так что перезапуск сервиса не теряет незавершённые вызовы: при старте агент восстанавливает ожидающие задачи из своих сессий и продолжает с того места, где остановился.

Цепочки вызовов отслеживаются. Агент не может вызвать сам себя, и не может участвовать в цикле, где он уже был. Каждый вызов несёт с собой список агентов, через которых прошла задача, и если в этом списке уже есть тот, кого собираются вызвать, вызов отклоняется с понятной ошибкой. Это защищает от бесконечных рекурсий, которые легко получить, когда два агента начинают звать друг друга.

### 📦 Изоляция проектов

У чата есть проекты. Проект — это сессия с идентификатором, который используется и в хранилище. Каждый проект получает свою папку в `projects/<id>/`. Изоляция не декоративная: модель проекта A не видит файлы проекта B, семантический поиск фильтруется по project_id, а агенты, вызванные из чата, работают в том же пространстве, что и вызвавший их чат. Проект чата определяет, куда агент пишет и откуда читает, без каких-либо дополнительных настроек.

Скиллы и rebuke — общие для всех проектов. Это осознанное решение: скиллы полезны в любой задаче, а rebuke описывает поведение агента вообще, а не в рамках одного проекта. Файлы проектов изолированы, знания агентов — нет.

## 🔧 Расширение

### Свой агент

Описывается в `config.toml` в секции `[[agents]]`: имя, адрес, системный промпт, модель, инструменты, режим скиллов. Запускается через `agent_server --agent-name <имя>` или через `control_center`.

### Свой скилл вручную

Скиллы лежат в `.local_storage/<storage_name>/.skills/`. Формат:

```
SKILL: название
FOR: имя агента
DESCRIPTION: краткое описание для семантического поиска

INSTRUCTION:
исходная задача

RHAI_CODE:
код на Rhai
```

### Свой rebuke

`/rebuke <agent> <текст>` дописывает замечание дословно. `/rebuke_edit <agent>` открывает файл в редакторе.

## 🌍 Ограничения

Однопользовательский режим. Изоляция проектов защищает от случайных ошибок, а не от намеренных. Враждебный пользователь со знанием внутренностей может обойти изоляцию — это осознанно, проект не рассчитан на враждебную среду.

Нет TLS. Все сервисы слушают localhost.

Логи чатов не ротируются.

Векторный индекс хранится в памяти и перестраивается при старте хранилища, если файлы изменились в обход API.

Godfather у агентов пока не реализован — только у чата.

## ⚙️ Конфигурация

Все настройки — в `config.toml`. Секреты — в нём или в `.env`, переменные окружения имеют приоритет.

### 🌐 Глобальные параметры

| Параметр | Тип | Что делает |
|----------|-----|-----------|
| `api_key` | строка | Ключ к API языковой модели. Переопределяется `POLZA_API_KEY`. |
| `base_url` | строка | Базовый адрес API. По умолчанию `https://polza.ai/api/v1`. |
| `model` | строка | Идентификатор модели. |
| `temperature` | число | Температура генерации, 0..2. |
| `max_tokens` | целое | Максимум токенов в ответе. |
| `top_p` | число | Nucleus sampling. |
| `stream` | bool | Потоковая передача. |
| `reasoning_effort` | строка | `low`, `medium`, `high`. |
| `max_cost_rub` | число | Бюджет в рублях. |
| `prefix_message_count` | целое | Сколько первых пар закрепляется в префиксе. |
| `tail_message_count` | целое | Сколько последних пар держится в скользящем окне. |
| `tail_byte_budget` | целое | Бюджет хвоста в байтах. |
| `compact_threshold_bytes` | целое | Порог механической компактизации. По умолчанию 512. |
| `system_prompt` | строка | Системный промпт чата. |
| `rhai_timeout_sec` | целое | Таймаут Rhai-скриптов. |
| `editor` | строка | Редактор для `/rebuke_edit`. |

### 🔧 Секция `[[tools]]`

```toml
[[tools]]
name = "run_code"
mode = "auto"    # auto — без подтверждения, manual — с подтверждением

[[tools]]
name = "local_storage"
mode = "auto"
```

### 🧠 Секция `[vector_db]`

| Параметр | Что делает |

### 💾 Секция `[local_storage_http_server]`

| Параметр | Что делает |
|----------|-----------|
| `bind_addr` | Адрес и порт сервера хранилища. |
| `storage_name` | Имя поддиректории внутри `.local_storage/`. |
| `auth_token` | Токен аутентификации. Переопределяется через `LOCAL_STORAGE_AUTH_TOKEN`. |

### 📨 Секция `[message_board]`

| Параметр | Что делает |
|----------|-----------|
| `bind_addr` | Адрес и порт доски. |
| `auth_token` | Токен. Переопределяется через `MESSAGE_BOARD_AUTH_TOKEN`. |
| `tasks_dir` | Где хранить JSON задач. По умолчанию `.board/tasks`. |
| `task_timeout_sec` | Через сколько секунд незавершённая задача помечается упавшей. |

### 👑 Секция `[godfather]`

| Параметр | Что делает |
|----------|-----------|
| `model` | Модель для сжатия контекста. |
| `api_key` | Ключ. Порядок приоритета: `GODFATHER_API_KEY` -> `POLZA_API_KEY` -> этот параметр. |
| `base_url` | Адрес API. |
| `temperature` | По умолчанию 0.3. |
| `max_tokens` | Лимит на резюме. |
| `prompt` | Системный промпт для сжатия. |

### 🤖 Секция `[[agents]]`

| Параметр | Что делает |
|----------|-----------|
| `name` | Уникальное имя. |
| `bind_addr` | Адрес и порт HTTP-сервера агента. |
| `auth_token` | Токен. Переопределяется через `AGENT_<ИМЯ>_AUTH_TOKEN`. |
| `timeout_sec` | Таймаут HTTP-запросов. |
| `max_iterations` | Максимум циклов за один ход. |
| `tools` | Массив имён разрешённых инструментов. |
| `system_prompt` | Системный промпт агента. |
| `api_key`, `base_url`, `model`, `temperature`, `max_tokens`, `top_p`, `stream` | Параметры LLM. |
| `reasoning_effort` | Уровень размышлений. |
| `rhai_timeout_sec` | Таймаут Rhai. |
| `agent_call_timeout_sec` | Таймаут `call_agent`. По умолчанию 120. |
| `agent_type` | `stateless` или `stateful`. |
| `session_ttl_secs` | Время жизни сессии. |
| `skill_mode` | `auto`, `manual` или `off`. |
| `skill_semantic_threshold` | Порог расстояния при поиске скиллов. |
| `skill_min_code_length` | Минимальная длина кода для сохранения. |
| `skill_auto_execute_threshold` | Порог автовыполнения скилла. |
| `max_cost_rub` | Бюджет в рублях. |
| `compact_threshold_bytes` | Порог компактизации. |
| `tail_byte_budget` | Бюджет хвоста. |

## 🌐 HTTP API хранилища

Заголовок `Authorization: Bearer <token>` обязателен. Публичные эндпоинты дополнительно требуют `X-NH-Project: <project_id>`.

### 📄 Файлы

| Метод и путь | Что делает |
|--------------|-----------|
| `GET /files?path=` | Читает файл. |
| `POST /files?path=` | Записывает файл. |
| `DELETE /files?path=` | Удаляет файл. |

### 📁 Директории и списки

| Метод и путь | Что делает |
|--------------|-----------|
| `POST /dirs?path=` | Создаёт директорию. |
| `GET /list?path=` | Список элементов. |
| `GET /walk?path=` | Рекурсивный обход. |

### 🔍 Поиск

| Метод и путь | Что делает |
|--------------|-----------|
| `GET /search?query=&top_k=` | Семантический поиск по проекту. |
| `GET /search_name?pattern=` | Поиск по имени. |

### 📝 Метаданные

| Метод и путь | Что делает |
|--------------|-----------|
| `GET /about?path=` | Читает `.about`. |
| `POST /about?path=` | Записывает `.about`. |
| `GET /summary?path=` | Читает `.summary`. |
| `POST /summary?path=` | Записывает `.summary`. |

### 📚 Скиллы

| Метод и путь | Что делает |
|--------------|-----------|
| `GET /skills/get?path=` | Читает файл скилла. |
| `POST /skills/put?path=` | Записывает и индексирует. |
| `POST /skills/delete?path=` | Удаляет и деиндексирует. |
| `GET /skills/list?path=` | Список файлов. |
| `GET /skills/search?query=&top_k=` | Поиск только по скиллам. |

### 🗣️ Выговоры

| Метод и путь | Что делает |
|--------------|-----------|
| `GET /rebukes/get?agent=` | Читает файл выговоров. |
| `POST /rebukes/put?agent=` | Перезаписывает файл. |

## 🤖 HTTP API агента

| Метод и путь | Что делает |
|--------------|-----------|
| `POST /agent/run` | Принимает `AgentRequest`, возвращает `AgentResponse`. |

Поля запроса: `prompt`, `project_id` (обязательные), `session_id`, `max_iterations`, `tools`, `system_prompt` (опциональные).

## 📂 Где что хранится

### 🗂️ Рабочие каталоги

```
nano_harness/
  config.toml
  .env
  .models/
    paraphrase-multilingual-MiniLM-L12-v2/
      config.json
      tokenizer.json
      model.safetensors
  .local_storage/
    <storage_name>/
      projects/
        <project_id>/
          .about
          .summary
          ...файлы проекта...
      .skills/
      .rebukes/
      vector_meta.json
  .sessions/
    chat_<session_id>.json
    agent_<agent>_<session_id>.json
    logs/
      chat_<session_id>.txt
      agent_<agent>_<session_id>.txt
  .board/
    tasks/
      <task_id>.json
```

### 💾 Хранилище

Корень — `.local_storage/<storage_name>/`. Проекты чата изолированы: каждый в `projects/<project_id>/`, изоляция обеспечивается заголовком `X-NH-Project`.

В каждой директории автоматически создаются `.about` и `.summary`. Доступны только через `/about` и `/summary`, через публичный API файлов их не достать.

`.skills/` — скиллы. В корне хранилища, вне проектов. Внутри:

- `skills_catalog.json` — каталог скиллов.
- `skill_agent_<agent>_<name>_<timestamp>.txt` — полный скилл.
- `skill_agent_<agent>_<name>_<timestamp>_description.txt` — описание для поиска.
- `skill_agent_<agent>_<name>_<timestamp>_prompt.txt` — исходный промпт.

`.rebukes/` — выговоры. Один файл на агента: `<agent>.txt`.

```
---[2026-09-26 17:04]--------
Не отвечай одним словом.

---[2026-09-26 17:16]--------
Не используй `mut` в Rhai.
```

`vector_meta.json` — метаданные векторного индекса. Восстанавливается при старте хранилища, если файлы изменились в обход API. Защищён от публичного API.

### 💬 Сессии

В `.sessions/`. JSON-файлы сессий чата и агентов. Атомарная запись через временный файл и переименование, блокировка через `fs2`, API-ключ маскируется на `***`.

Логи в `.sessions/logs/`. Строки: время, роль, содержимое. Содержимое `tool_result` здесь полное, в отличие от контекста сессии.

### 📨 Доска

Задачи в `.board/tasks/`. Один JSON на задачу. Незавершённые не теряются при перезапуске — агент подгружает их из своих сессий.

### 🐛 Отладка

Модель ведёт себя странно — `.sessions/chat_<project_id>.json`.

Агент сделал не так — `.sessions/agent_<agent>_<session_id>.json` и `.sessions/logs/agent_<agent>_<session_id>.txt`.

Скилл не сохранился — `.local_storage/<storage_name>/.skills/skills_catalog.json` и лог агента, искать `skill_found`, `skill_saved`, `skill_skipped`, `skill_skipped_duplicate`.

Задача потерялась — `.board/tasks/<task_id>.json` и лог агента-получателя.

Файлы пропали из поиска — `vector_meta.json` в корне хранилища.
